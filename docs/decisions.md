# Decisions

Each decision is numbered and stays here even when superseded, with a note on what replaced it. Open questions move here once they are answered.

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Home | A Liminal HQ Labs experiment in `liminal-hq-labs/undertone-sound`, public from the first commit | Try the idea in the open before it earns a place in Liminal HQ |
| D2 | Licence | `Apache-2.0 OR MIT` | House licence, compatible with both ecosystems |
| D3 | Dependency updates | No Dependabot configuration until the project opts in | Labs repositories stay quiet by default. See the [Labs charter](https://github.com/liminal-hq-labs/.github/blob/main/docs/labs-charter.md#dependabot-is-opt-in) |
| D4 | Family and names | Undertone is a family: `undertone` (the TypeScript library, its own repository), `undertone-dsp`, `undertone-mini`, `undertone-opl` and `undertone-sound` (crates here), and `oplstream`, which stays unprefixed | `oplstream` names a format library that is useful without Undertone. Nothing is reserved on crates.io yet |
| D5 | First crate | `oplstream` is the reference implementation of OPX: reader, writer, stepper, validator, text twin, and IMF, DRO and VGM import | OPX is the DOS sound format and the core's register-stream format |
| D6 | OPX specification | `docs/OPX.md` lives here and moves with the crate; Fizz 2's docs point at this repository | The spec and its reference code change together. Maintainer's call, 2026-11-18 |
| D7 | Fizz-agnostic core | Fizz concepts (rooms, role pans, the level rule, captions, cue sheets, mix profiles) live in a separate Fizz layer outside this repository | A second consumer, City Sim 1000, shares Undertone. VoiceParams field names and builder method names are frozen, and any Rust or WebAssembly backend is opt-in |
| D8 | Neutral wording | Superseded 2026-11-18: the project carries no variant word of that kind. Names say what a thing is, and nothing here depends on the studio's old wording | The word described one Fizz 1 song variant; it has no value as a mode, format or name |
| D9 | Publishing | Every crate has `publish = false` until the maintainer says otherwise. Names are planned for crates.io but not reserved | Publish deliberately, with versions and a release flow decided first |
| D10 | Sound-effect channels | Channels 5 and 14 are the sound-effect channels on OPL2 and OPL3, passed in as reserved channels rather than hard-coded in the core | Fizz's choice; the core stays agnostic |
| D11 | Relicensing the carved crates | Crates carved from the Fizz Audio Studio are relicensed from MIT to `Apache-2.0 OR MIT`, and their SPDX headers change with them | The maintainer approved it on 2026-11-18, and this repository's licence is D2. The copyright line is unchanged |
| D12 | `undertone-mini` | It holds Undertone's mini-notation (parser, pattern combinators, exact fractions) and, as `js`, the JavaScript number and string semantics (`String(n)`, `toFixed(2)`, `Math.round`, `trim`, UTF-16 lengths, `JSON.stringify` quoting). `undertone-dsp` depends on it | Both exist so Rust output matches the TypeScript golden fixtures, and the mini-notation crate depends on nothing |
| D13 | What stays in the studio | The glue that turns a studio `Song` and `Performance` into Undertone voices and score events (`presets` and `studio`), and the comparison harness against the MPL-2.0 `web-audio-api` crate (`reference`), stay in the Fizz Audio Studio, which depends on `undertone-dsp` | This repository is Fizz-agnostic (D7) and keeps its default build free of an MPL-2.0 dependency. The allocation-counting streaming test also stays there, because it needs `unsafe` for a global allocator |
| D14 | Twin assembler needs `alloc` | `print_twin` is in the `no_std` core; `assemble` (twin text to bytes) needs `alloc` | A parser that produces bytes has to allocate. The specification lists both in the core |
| D15 | Other chips in a VGM file | A VGM file is refused when its header names no YM3812 or YMF262, names both, or sets the dual-chip flag. Other chips' commands inside an OPL file are dropped, counted in the import report, and their waits kept. An unknown VGM opcode is refused | The specification says other chips' commands are "dropped and reported" |
| D16 | Reader versions | A reader accepts major 0 with minor 0 or 1 and refuses a higher minor. `LOOP` while the tier is 1, and core writes to bank 1 when flag bit 0 is set, are refused. A loop point that lands on the `END` tick is refused | The most literal reading of the specification. Raise a question in the specification when a real file disagrees |
| D17 | Re-timing | Halves round up. "Writes moved" counts register and speaker writes whose tick did not map exactly. Markers and the loop point are re-timed but not counted | One rule, reported, never silent |
| D18 | CI shape | One job per check in the shared `ci-rust` image pinned by digest (format, Clippy, tests, doc tests, docs, `oplstream` feature tiers, `no_std` build, WebAssembly build, dependency licences, advisories), plus markdown, headers, shell, workflow and banner checks on the runner | A failing pull request names exactly what broke. No single validate job. Dependabot stays off |
| D19 | Documentation site | VitePress with Bun in `site/`, deployed to GitHub Pages from `main` by `.github/workflows/pages.yml`. The specification, behaviour, roadmap and decisions pages are rendered from `docs/OPX.md`, `SPEC.md`, `docs/ROADMAP.md` and `docs/decisions.md` by include, so each stays the single source and no copy is committed. The Rust API is `cargo doc` output copied into the site under `api/` by `scripts/build-site.sh`. The guide pages show snippets from an example in each crate (`examples/*_guide.rs`), which the test build compiles | The house pattern from Undertone's own site, in this project's colours. Documents that live in the repository for readers on GitHub should not fork. Compiled snippets cannot drift from the API. The site builds on every pull request in one `Docs site` job and deploys only on `main` |
| D20 | WebAssembly bindings | `crates/undertone-wasm` (`cdylib` and `rlib`, `publish = false`) exposes the crates to JavaScript with `wasm-bindgen` pinned at `=0.2.125`, the version of the `wasm-bindgen` tool in the shared `tauri-ci-desktop` image. `scripts/build-wasm.sh` refuses to run when the two differ. The logic is plain Rust in modules tested natively, and the exported layer is thin. Failures cross as thrown strings | A version mismatch between the crate and the tool is a runtime failure, so it is checked first. Native tests keep the logic out of the browser |
| D21 | OPL emulator and `unsafe` | The player uses `oplon` `=1.0.0` (MIT, `no_std`, integer-only OPL2 and OPL3), the emulator the studio plays OPL with. No `unsafe_code` exception is needed: the workspace's `forbid(unsafe_code)` compiles with `wasm-bindgen`'s macros on native and `wasm32` targets | The licence is already allowed by `deny.toml`. If a later `wasm-bindgen` needs an exception, scope it to `undertone-wasm` and record it here |
| D22 | Demo page | `site/demo.md` renders the whole stream through `Player` in blocks on the main thread, then plays it as one `AudioBuffer`, and shows the peak it rendered. Only Title Theme, the maintainer's own composition, is bundled, imported by Vite from `fixtures/opx/title-theme.imf` so no copy exists. Other songs are dropped in by the visitor and never leave the browser | The simplest approach that is exact and checkable. No third-party game music is bundled |
| D23 | Readable errors | `HeaderError`, `DecodeError` and `ValidationError` implement `Display`, in the `no_std` core | A page or a tool shows why a file was refused without matching on enums |
| D24 | CI for the bindings | A `WebAssembly bindings` job runs `scripts/build-wasm.sh` (the release build and `wasm-bindgen`) in the `tauri-ci-desktop` image, which carries the `wasm32` target and the pinned `wasm-bindgen`. The `Docs site` job and the Pages workflow run the same script through `scripts/build-site.sh`, so the demo ships in the site | One job per check, as D18 says |
| D25 | DSP provenance wording | `undertone-dsp` documents that it implements the specification's algorithms and matches Chromium's behaviour. It does not claim a clean-room derivation, and the compressor stays `Apache-2.0 OR MIT` | The compressor's provenance against Chromium's BSD-3-Clause kernel is unverified, so the wording claims only behaviour. The maintainer decided the licence, 2026-11-18 |
| D30 | What `undertone-sound` holds | The song document and what a host does with it before any sound: `model`, `validate`, `format`, `music`, `pan`, `takes`, `compile` and the private `mini_bridge`. It depends on `undertone-mini`. The studio keeps the editor file (`file`), albums (`album`), the text readout (`describe`) and change summaries (`summarise`) | Those four are host features (file extensions, album manifests, prose for a model, change lists), not the document. `js` already lives in `undertone-mini` (D12) |
| D31 | Frozen song vocabulary | Superseded by D50, D51 and D52 (the format id, the presets and the host codes, and the author words). Was: The format id `fizz-audio-studio/song` and version 1 are kept byte for byte, and so are the other words existing song files hold: engine ids (`undertone`, `opl2`, `opl3`, `pc-speaker`), the thirteen preset names (including `bass-saw`, `pad-bright` and `drone`), author words (`you`, `claude`) and every `ProblemCode`, including the codes for album manifests, editor files and comment files, which this crate never raises. All of it is documented in this crate without Fizz wording. A version gate agreed with the studio changes them together, and the preset names and host codes then become host-supplied | Renaming a word in the format breaks every song file and the studio's generated TypeScript. The three DOS preset names are only names here: the patches they select live with the OPL layer and are supplied by the host, never held in this repository |
| D32 | TypeScript bindings | Partly superseded by D53 (the studio generates from this crate). Was: `ts-rs` is an optional dependency behind the `ts` cargo feature, off by default. The derives are gated with `cfg_attr`, and the bindings go to the crate's `bindings/` directory (ignored by git). The studio keeps generating the TypeScript its UI imports from its own copy of the types until the version gate | The default build carries no code generator, and this repository does not write into another repository's `packages/`. The generated shapes were compared with the studio's for all 32 types and match apart from doc comments |
| D33 | Song fixtures | Superseded by D54 (the song fixtures are written here). Was: `fixtures/song/` holds the studio's recorded `compile`, `formatted`, `model`, `music` and `validation` files and the named songs they use, copied as static JSON. The files that cover studio features (`albums`, `changes`, `describe`, `edits`, `edit-exports`, `files`, `playlist`, `summaries`) stay there. Regenerating is done in the studio | They are shared contracts written by the TypeScript implementation; this repository only reads them |
| D34 | What `undertone-opl` holds | The register sequencer and channel allocator (`sequence`), registers, the OPL3 pan law (`stereo`), patches, lost-note accounting (`limits`), the PC speaker (`speaker`), the `oplon` renderer (`chip`) and a trimmed `engine` (sequence or render a song or a track's share of the mix). It depends on `undertone-sound`, `undertone-mini` and `oplon` 1.0.0. The studio keeps the engine listing and placement readouts, the voice parameter tables (`params`), `spread`, `stereo_view` and the IMF writer and reader (`imf`) | The kept code is what a game or tool needs to lower a song to a chip; the rest is the studio's editor and its DOS converter. The importer for IMF is in `oplstream` already |
| D35 | Host profile | Partly superseded by D51 (the three presets are gone, and a bank holds a patch for every preset). Was: The sequencer takes an `OplProfile` holding the reserved channels and a patch bank, in place of the studio's `SFX_CHANNELS` constant and its three built-in game patches. Channels are numbered 0 to 17, with 9 and up on the OPL3's second bank; the melodic channels of a chip are all of them except 6 to 8 of the first bank (the rhythm section) and the reserved ones. The crate holds the patches of ten presets, and `bass-saw`, `pad-bright` and `drone` have none: a bank answers them with the `lead` patch until the host supplies theirs. The default profile reserves nothing | D10 says the core stays agnostic about which channels a game keeps for sound effects. The three patches were the game's own and are the host's data. The recorded fixtures pass with a test that reserves `[5, 14]` and supplies the three patches itself |
| D36 | Chip fixtures | `fixtures/chips/` holds the studio's recorded `opl2`, `opl3`, `speaker`, `lost`, `registers`, `render` and `pan` files and its three songs of its own, copied as static JSON. `voice-params.json` and `voice-values.json` stay in the studio with the code that makes them, and the `placements` of `pan.json`, which come from the studio's readouts, are recorded but not read. The renders match to 1e-6 | The same contract as D33. The file `chips-fizz.song.json` keeps its recorded name; it is the song that uses the three presets a host supplies |
| D37 | OPX export | `undertone_opl::opx::export_opx` turns an `OplSequence` into an OPX file on a grid the host names. It rounds each write to a tick and offers three mechanics, each off by default: `headroom` (steps of 0.75 dB on every melodic carrier), `KeyOffs::BeforeNextKeyOn` (a note ends no later than the tick before the next on its channel, and no sooner than a tick after it began) and `DrumHolds::Ticks` (each rhythm drum held a fixed number of ticks, or until struck again). It never writes registers 0x104 and 0x105, which `docs/OPX.md` gives to the host's audio service, and the header's `reserved_channels` are the profile's, limited to the chip's channels. The studio's IMF writer is not carried over: its level rule, its channel ranking and its setup order are one game's habits | The mechanics are what any converter to a coarse grid needs, and they are parameters. The game's rules are the host's, and the Title Theme test and example hold them |
| D38 | Title Theme proof | The input is the 36-bar DOS arrangement of Title Theme (`fixtures/song/inputs/title-theme-dos.song.json`), not the 8-bar loop the studio calls `title-theme`: the game's chunk is 34,560 ticks, which is 36 bars at 140 bpm. The test plays the host: channels 5 and 14 reserved, 560 Hz, the game's level rule (each melodic note against the loudest, drums at full level), the ranking of notes that start together, six steps of headroom and drum holds of 40, 30, 40, 60 and 14 ticks. The OPL2 stream has the game's length, 644 notes and 316 drum hits, and the same notes by start, end, pitch and patch with channels ignored; four carrier levels differ, each eight steps quieter here (the breakdown's bass, which the game plays at full gain). 2,995 of the game's 3,312 register writes are identical in tick, register and value; the rest are the setup (the game writes the patches of the drums it strikes in its own order, and this stream writes every drum's) and the register writes of the channels that differ. The OPL3 stream has the same length and hits, 676 notes (the 32 the OPL2 drops and the one it cuts short, whole), each note on both outputs with a carrier four steps quieter, as the pan law's -3 dB per side gives. The OPL3 stream has no counterpart in the game | Equivalence is by what the stream sounds, as the studio's comparison with the game's chunk defines it, and not by bytes. Nothing here says the files play in Fizz 2's player: loading them there is the studio's contract test, and nothing has run on hardware |
| D39 | OPX goldens | `fixtures/opx/title-theme.opl2.opx` and `.opl3.opx` are written by `cargo run -p undertone-opl --example title_theme_opx`, each with its text twin (`.opx.txt`). `tests/title_theme_opx.rs` regenerates all four and requires them to match byte for byte, validates both streams and assembles each twin back to its stream | The files change only when the sequencer, the exporter or the song does, and the diff then shows in the twin |
| D40 | Test results on pull requests | [pr-results](https://github.com/liminal-hq-labs/pr-results) v0.4.1, pinned by commit SHA, posts one comment and a check run per suite. CI jobs only upload reports as artefacts: nextest JUnit (`ci` profile in `.config/nextest.toml`, one retry so a flaky test is reported as flaky) and a step report from each job, written by `scripts/step-report.sh`. `.github/workflows/publish-test-results.yml` publishes from a `workflow_run` trigger. Job names, and so check names, stay as they were | The repository is public, so fork pull requests get a read-only token and in-job publishing cannot post for them. The publisher holds the write tokens, runs from the default branch and never checks out pull request code. The existing jobs stay split, one per check (D18) |
| D41 | Two tracks | The roadmap has two named tracks. Track 1, the Undertone engine in Rust, is primary: the full API (patterns, controls, signals, scheduling), native rendering without Web Audio, the JavaScript surface through WebAssembly, 0.4.0 parity and a parity canary against the TypeScript library, with City Sim 1000's API frozen. Track 2, synth backends, OPX and DOS, extends the engine to chips and other synths, so its interface is a general backend and OPL is the first. New OPL-only work waits for Track 1's design | The maintainer's direction, 2026-11-18: Undertone's audio engine is the core product and the supporting layers extend it to DOS and other synths. This project is the testing ground for a Rust-first Undertone |
| D42 | Engine below, backends above | `undertone-mini` and `undertone-dsp` depend only on each other and on registry crates. Song, OPL, OPX and binding crates depend on them, never the reverse. The engine's own JavaScript bindings will be a separate crate from `undertone-wasm`, which today also carries OPX. `scripts/check-layering.sh` and the `Crate layering` job enforce it | The Undertone repository may move to Rust and WebAssembly behind the same JavaScript package; the engine crates must then be promotable with their history. Nothing is decided; this keeps the option open |
| D50 | Neutral song id, version reset | The song format id is `undertone-sound/song` and the version is 1. A file with the old id `fizz-audio-studio/song` is refused (`wrong-format`); there is no shim and no second id. The engine ids `undertone`, `opl2`, `opl3` and `pc-speaker` stay as they are until a backend interface owns them | Supersedes the id and version half of D31. The studio has no compatibility constraint, and the id named a product this crate does not know (D7). The version restarts because the format restarts: nothing written under the old id is read |
| D51 | Fizz presets are host data | `PresetId` has ten presets: `lead`, `square-lead`, `soft-lead`, `pluck`, `bell`, `pad`, `organ`, `bass`, `sub-bass` and `kit`. `bass-saw`, `pad-bright` and `drone` are removed, and a song that names one fails validation (`bad-preset`). A host that wants a sound of its own supplies it as data for an engine: `undertone_opl::OplProfile::with_patch` replaces the patch of the preset the sound belongs to, and `PatchBank` now holds a patch for every preset, so `standard_patch` returns a `Patch` and `PatchBank::contains` is gone. The other ten are kept because their names say a role of timbre, not a product, and the OPL layer holds a patch for each. `ProblemCode` loses the ten variants this crate never raised: `bad-description`, `bad-songs`, `bad-song-id`, `duplicate-song`, `not-valid-json`, `bad-comments-file`, `bad-thread`, `bad-comment`, `bad-anchor` and `comments-limit`. Album, editor-file and comment-file formats are the studio's and are not named here | Supersedes the preset, host-code and `ProblemCode` half of D31 and the three-preset fallback in D35 (a bank used to answer them with `lead`). A preset is the format's word, and a game's patch is the game's data (D7, D35) |
| D52 | Author type | A take's and a message's `by` is an `Author`: an object with a `kind` (`human` or `agent`, the type `AuthorKind`) and an optional `name`. Only an agent has a name, which is non-empty free text; an unknown field in an author is the usual `unknown-field` warning; a bad author is `bad-author` at the field that is wrong (`by`, `by.kind` or `by.name`). `Author::human()`, `Author::agent()` and `.named(name)` build one. A host maps its own words onto the two kinds | Supersedes the `you` and `claude` words of D31. The object leaves room for more than a word without another format change, and reads as a plain pair in JSON and in TypeScript (`{ kind: AuthorKind, name?: string }`, with `AuthorKind` the words `human` and `agent`) |
| D53 | TypeScript export route | `cargo test -p undertone-sound --features ts` writes the generated TypeScript into `crates/undertone-sound/bindings/` (ignored by git), and the `TS_RS_EXPORT_DIR` environment variable names another directory (`ts-rs` 12 reads it; a relative path is taken from the crate's directory). The layout is `ts-rs`'s: one file per type, named after it, each importing the files it uses, and no index. `tests/bindings.rs` exports the song, validation and performance types to a scratch directory and checks the layout, so the `Song TypeScript bindings` job proves the export works and the shapes a host depends on. The studio generates from this crate and drops its own copies | Supersedes the second sentence of D32 (the studio keeps generating from its own copy of the types until a version gate). The mechanism is `ts-rs`'s own and needs no code here; the work is to document it and test it |
| D54 | Rust-canonical song fixtures | `fixtures/song/` is written by this repository. Each test in `crates/undertone-sound/tests/` computes a file from the cases it holds (inputs stay, results are made) and requires the file to hold exactly that text; `UPDATE_FIXTURES=1 cargo test -p undertone-sound -- --test-threads=1` writes the files instead, and the diff shows what a change did. The song documents in `fixtures/song/inputs/` and `fixtures/chips/inputs/` are checked to be in the song style. `fixtures/chips/inputs/chips-fizz.song.json` is renamed `chips-host-patches.song.json` and its instruments name `bass`, `pad` and `organ`; the host test plays the same three patches for that song only, so the recorded chip results are unchanged. The `mini/`, `undertone/` and `chips/` results stay recorded from the TypeScript | Supersedes D33 and the file name in D36: the song fixtures are no longer recorded from the studio, because the format they hold is no longer the studio's. `compile.json` is byte for byte what it was, since the compiler did not change |
| D60 | No decisions page on the site | The site does not render `docs/decisions.md`: there is no page, no navigation or sidebar entry and no rewrite or include for it. A link to it from a rendered document points at the file in the repository on GitHub. The file stays in the repository, and `README.md` and `AGENTS.md` keep referring to it | It is a contributor record of why the project is the way it is, not documentation for someone using the crates or the format. Keeping it out of the site keeps the site to what a visitor can use |
| D61 | Demo: Title Theme three ways | The demo shows Title Theme as one card each for the Undertone engine, the OPL2 chip file and the OPL3 chip file. The Undertone card reads the recorded `title-theme` score from `fixtures/undertone/graph.json` (imported by Vite from the fixture, never copied) through `undertone-wasm`'s `ScorePlayer`, which books it with `undertone-dsp` at 112 ticks a second and streams it through `Engine`; the case is bars 1 and 2 of the studio's eight-bar arrangement, 3.43 s. The chip cards play `fixtures/opx/title-theme.opl2.opx` and `.opl3.opx` through `oplon`. The three are different arrangements and the page says so. Only one plays at a time. Switching between the two chip versions continues from the same moment, since they share one arrangement and grid; the Undertone card always starts from its beginning. Supersedes D22's choice of the IMF as the bundled song; a visitor's own IMF, DRO, VGM or OPX file still works | The maintainer asked for the original Undertone version beside the chip versions, and for the OPL3 file. The recorded score is the only Undertone rendering of Title Theme the repository holds, and it is a two-bar excerpt, so the page does not pretend it is the whole song. A shared timeline would be false across arrangements, so it is offered only where it is true |
